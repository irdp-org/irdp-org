# ระบบเอกสาร QMS (ISO 9001:2026) — การออกแบบ

อ้างอิง: `PM-DCC-01 การควบคุมเอกสารและข้อมูล` และ `SD-DCC-01-01 ตารางสิทธิ์การทบทวนและอนุมัติเอกสาร`
(ประกาศใช้ 5 พ.ย. 2569)

---

## 0. ข้อควรแก้ก่อนเริ่ม — ชื่อลำดับการอนุมัติ

ที่คุยกันไว้ใช้คำว่า **ผู้จัดทำ → ผู้อนุมัติ → ผู้รับรอง**
แต่เอกสาร ISO จริง (ทั้งหน้าปก PM-DCC-01 และ SD-DCC-01-01) ใช้ว่า:

| ลำดับ | ชื่อในเอกสาร ISO | ความหมาย |
|---|---|---|
| 1 | **ผู้จัดทำ** (Author) | คนเขียนเอกสาร |
| 2 | **ผู้ทบทวน** (Reviewer) | หัวหน้าฝ่าย/ผู้อำนวยการ — ตรวจความเหมาะสมและความเพียงพอ |
| 3 | **ผู้อนุมัติ** (Approver) | ระดับบริหาร (รองกรรมการผู้จัดการ / QMR / กรรมการผู้จัดการ) |

**ระบบต้องใช้คำชุดนี้** เพราะต้องตรงกับช่องลงนามบนหน้าปกเอกสารทุกฉบับ
ถ้าใช้คำอื่นจะไม่ตรงกับเอกสารที่ประกาศใช้ไปแล้ว และจะมีปัญหาตอน audit

---

## 1. หัวใจของการออกแบบ — ผู้อนุมัติมาจากตารางสิทธิ์ ไม่ใช่จาก "หัวหน้าฝ่าย"

ที่บอกว่า *"ผู้อนุมัติก็ต้องเป็นหัวหน้าฝ่ายของผู้จัดทำคนนั้น"* — จริง ๆ แล้ว
`SD-DCC-01-01` กำหนดไว้ละเอียดกว่านั้นมาก และกำหนดเป็น **ตำแหน่ง** ไม่ใช่ตัวบุคคล
โดยคีย์ด้วย **(รหัสกระบวนการ, ประเภทเอกสาร)**:

| กระบวนการ | ประเภท | ผู้จัดทำ | ผู้ทบทวน | ผู้อนุมัติ |
|---|---|---|---|---|
| PA (ประเมินผล) | PM/WI/FM/SD | ผู้ช่วยผู้จัดการขึ้นไป | ผู้อำนวยการฝ่าย | รองกรรมการผู้จัดการ |
| RD (วิจัย) | PM/WI/FM/SD | นักวิจัยอาวุโส | รองผู้จัดการฝ่าย | รองกรรมการผู้จัดการอาวุโส |
| TR, SALE (ฝึกอบรม/ขาย) | PM/WI/FM/SD | ผู้ชำนาญการฝึกอบรมขึ้นไป | ผู้จัดการฝ่าย | รองกรรมการผู้จัดการอาวุโส |
| HR, ADM (ธุรการ/จัดซื้อ) | PM/WI/FM/SD | ผู้ชำนาญการธุรการขึ้นไป | ผู้อำนวยการฝ่าย | รองกรรมการผู้จัดการอาวุโส |
| FIN (บัญชี) | PM/WI/FM/SD | นักบัญชีอาวุโส | ผู้อำนวยการฝ่าย | รองกรรมการผู้จัดการอาวุโส |
| IT | PM/WI/FM/SD | รองผู้จัดการ | ผู้อำนวยการฝ่าย | รองกรรมการผู้จัดการอาวุโส |
| MGT (บริหาร) | QM, SD | ผู้ช่วย QMR | **QMR** | **กรรมการผู้จัดการ** |
| QMS | PM/WI/FM/SD | ผู้ช่วย QMR | ผู้ช่วย QMR | QMR |
| DCC | PM/WI/FM/SD | เจ้าหน้าที่ DCC | ผู้ช่วย QMR | QMR |

**แปลว่า:** พอ DCC พิมพ์รหัสเอกสาร เช่น `PM-DCC-01` ระบบแกะได้เลยว่า
`PM` = ประเภท, `DCC` = กระบวนการ → เปิดตารางสิทธิ์ → ได้ว่าผู้ทบทวนคือ "ผู้ช่วย QMR",
ผู้อนุมัติคือ "QMR" → แล้ว map ตำแหน่งนั้นไปหาตัวพนักงานจริง → **เติมให้อัตโนมัติ**
DCC แค่กดยืนยัน หรือแก้ชื่อเองได้ถ้าต้องการ (กรณีมอบหมาย/คนลา)

นี่คือการทำ **กิจกรรมที่ 1** ของ PM-DCC-01 ให้เป็นระบบ แทนที่จะเป็นตาราง Excel

> ตารางสิทธิ์ต้องเก็บเป็นตารางในฐานข้อมูล แก้ไขได้ผ่านหน้าจอ (ไม่ hardcode)
> เพราะ PM-DCC-01 ระบุให้ DCC ทบทวนรายชื่อผู้มีสิทธิ์อย่างน้อยปีละ 1 ครั้ง

## 2. โครงสร้างข้อมูล

### `qms_documents` — ทะเบียนควบคุมเอกสาร (= FM-DCC-01-04)
```
id, doc_code            PM-DCC-01
doc_type                QM | PM | WI | FM | SD
process_code            DCC | HR | RD | ...
title                   การควบคุมเอกสารและข้อมูล
revision_no             0, 1, 2, ...        ← ครั้งที่แก้ไข
effective_date          2569-11-05          ← วันที่มีผลบังคับใช้
confidentiality         public | internal | confidential   ← ชั้นความลับ (ข้อ 1.6)
status                  draft | pending_author | pending_reviewer
                        | pending_approver | approved | published
                        | returned | obsolete
process_owner_id
source_pdf_drive_id     ไฟล์ที่ DCC อัปโหลด (ยังไม่มีลายเซ็น)
source_docx_drive_id    ไฟล์ Word ต้นฉบับ (เก็บไว้ตามข้อ 1.5)
published_pdf_drive_id  ไฟล์ที่ลงนามครบแล้ว ← อันนี้คือฉบับควบคุม
published_sha256        ลายนิ้วมือไฟล์ ใช้ตรวจว่าไม่ถูกแก้
supersedes_id           เอกสารฉบับเดิมที่ถูกแทนที่
obsoleted_at, obsolete_reason
last_reviewed_at        ← ใช้เตือนทบทวนปีละครั้ง (กิจกรรมที่ 11)
```

### `qms_approvals` — ขั้นการลงนาม
```
id, document_id
step_no                 1 | 2 | 3
role                    author | reviewer | approver
employee_id
position_snapshot       ตำแหน่ง ณ วันลงนาม ← สำคัญ! ตำแหน่งเปลี่ยนภายหลังได้
status                  waiting | current | approved | rejected
acted_at
signature_url_snapshot  สำเนาลายเซ็น ณ วันลงนาม
comment                 ความเห็น / เหตุผลที่ตีกลับ
```

> **ทำไมต้อง snapshot ตำแหน่งกับลายเซ็น:** เอกสารที่ลงนามไปแล้วต้องไม่เปลี่ยน
> ถ้าภายหลังคนนั้นเลื่อนตำแหน่งหรือเปลี่ยนลายเซ็นในโปรไฟล์ เอกสารเก่าต้องคงเดิม

### `qms_events` — audit trail
ทุกการกระทำ: upload / assign / approve / reject / publish / obsolete
พร้อม `actor_id`, `at`, `detail` — ใช้เป็นหลักฐานตอน audit

### `qms_authority_matrix` — ตารางสิทธิ์ (= SD-DCC-01-01)
```
process_code, doc_type, author_position, reviewer_position, approver_position
```

## 3. Flow การใช้งาน

```
DCC อัปโหลด PDF + กรอกรหัส/ชื่อ/วันที่มีผล
        │
        ├─ ระบบแกะรหัส → เปิดตารางสิทธิ์ → เติมชื่อ 3 คนอัตโนมัติ
        │  (DCC แก้ได้)
        ▼
   กด "ส่งอนุมัติ"  → แจ้งเตือนทั้ง 3 คน (LINE + ในระบบ)
        │              แต่กดได้เฉพาะ "ผู้จัดทำ" เท่านั้น
        ▼
   1. ผู้จัดทำ  เปิดดู PDF → ✅ อนุมัติ  ──┐
        ▼                                  │ ❌ ตีกลับ (ใส่เหตุผล)
   2. ผู้ทบทวน  เปิดดู PDF → ✅ อนุมัติ  ──┤   → กลับไปที่ DCC
        ▼                                  │     status = returned
   3. ผู้อนุมัติ เปิดดู PDF → ✅ อนุมัติ  ──┘     DCC แก้ไฟล์แล้วส่งใหม่
        ▼
   ครบ 3 คน → ระบบสร้าง PDF ฉบับลงนาม (ดูข้อ 4)
        ▼
   DCC กด "ประกาศใช้" → ขึ้น Drive + ฉบับเดิม → OBSOLETE
```

**กฎสำคัญ:**
- กดได้ทีละคนตามลำดับ — คนที่ยังไม่ถึงคิวเห็นได้แต่กดไม่ได้
- ตีกลับได้ทุกขั้น → ย้อนกลับไปที่ DCC ทั้งหมด (ไม่ใช่ย้อนทีละขั้น)
  เพราะคนแก้ไฟล์คือ DCC อยู่ดี
- **ประกาศใช้ต้องล่วงหน้า ≥ 3 วันทำการ** ก่อน `effective_date` (กิจกรรมที่ 7)
  → ระบบควรเตือนถ้า DCC ตั้งวันที่ใกล้เกินไป

## 4. การแทรกลายเซ็นลง PDF — 3 วิธี

นี่คือคำถามหลักที่ถามมา สรุปทางเลือกให้ครบ:

### วิธี A — สร้าง "หน้ารับรองการอนุมัติ" แล้วรวมไฟล์ ⭐ แนะนำให้เริ่มจากอันนี้

ระบบสร้าง PDF หน้าเดียว หน้าตาเหมือนตารางลงนามบนหน้าปก แต่เติมลายเซ็น/ชื่อ/
ตำแหน่ง/วันที่จริง แล้วเอาไป **รวมกับ PDF ที่อัปโหลด** เป็นไฟล์เดียว

```
[หน้ารับรองการอนุมัติ]  +  [PDF QMS ที่อัปโหลด]  →  ไฟล์เดียว
```

- **ข้อดี:** ใช้ได้กับ PDF ทุกไฟล์ทันที ไม่ต้องแก้ template Word เลย
  ใส่ข้อมูลเพิ่มได้ เช่น เวลาที่กดอนุมัติจริง (ชั่วโมง:นาที), SHA-256,
  QR code สำหรับตรวจสอบ — ซึ่ง **เป็นหลักฐานที่แข็งกว่าลายเซ็นสแกนเฉย ๆ**
- **ข้อเสีย:** เป็นหน้าเพิ่ม ไม่ได้เซ็นลงบนตารางหน้าปกเดิม
- **เทคนิค:** HTML → Puppeteer → PDF แล้วใช้ `pdf-lib` merge

### วิธี B — ฝังโค้ดในไฟล์ Word แล้วให้ระบบหาพิกัดเอง ⭐ ตรงกับที่ถามที่สุด

ที่ถามว่า *"มีไฟล์ word ด้วย สามารถแฝงโค้ดอะไรไว้ก็ได้"* — ทำได้ และนี่คือวิธี:

1. ใน template Word ช่องลงนาม ใส่ข้อความ marker:
   ```
   {{SIG:AUTHOR}}  {{NAME:AUTHOR}}  {{POS:AUTHOR}}  {{DATE:AUTHOR}}
   {{SIG:REVIEWER}} ...
   {{SIG:APPROVER}} ...
   ```
   ตั้ง **สีขาว + ขนาด 1pt** → มองไม่เห็นตอนพิมพ์ แต่ยังอยู่ในไฟล์
2. Export เป็น PDF ตามปกติ (workflow เดิมไม่เปลี่ยน)
3. ระบบอ่าน PDF ด้วย `pdfjs-dist` ซึ่งคืน **พิกัด x/y/หน้า ของข้อความทุกชิ้น**
   → หาตำแหน่ง marker ได้แม่นยำ
4. ใช้ `pdf-lib` วาดรูปลายเซ็น + ข้อความไทยทับลงตรงนั้นพอดี

- **ข้อดี:** ลายเซ็นลงบนตารางหน้าปกจริง ๆ ไม่มีหน้าเพิ่ม, ยังใช้ Word เหมือนเดิม,
  ย้าย template ได้โดยไม่ต้องแก้โค้ด (พิกัดมาจาก marker ไม่ได้ hardcode)
- **ข้อเสีย:** ต้องไปใส่ marker ใน template ทุกฉบับก่อน, ต้อง embed ฟอนต์ไทย
  (ใช้ Sarabun) เพราะ `pdf-lib` ไม่มีฟอนต์ไทยมาให้

### วิธี C — docxtemplater แก้ Word ตรง ๆ แล้วแปลงเป็น PDF ❌ ไม่แนะนำ

ต้องมี LibreOffice/Gotenberg บนเซิร์ฟเวอร์เพื่อแปลง docx→pdf
ซึ่ง **รันบน Vercel ไม่ได้** ต้องแยก service ออกไปอีกตัว — ไม่คุ้ม

### สรุปที่แนะนำ

> **Phase 1 ทำวิธี A** — ได้ใช้งานจริงเร็วที่สุด ไม่ต้องแตะ template เลย
> **Phase 2 เพิ่มวิธี B** — พอใส่ marker ใน template ครบแล้ว ระบบจะเซ็นลงหน้าปกให้
> แล้ว**ยังแนบหน้ารับรองของวิธี A ต่อท้ายไว้ด้วย** เพราะหน้านั้นมี timestamp +
> QR ตรวจสอบ ซึ่งผู้ตรวจ ISO ชอบมาก

### Library ที่ต้องใช้
| ใช้ทำอะไร | ตัวที่ใช้ | หมายเหตุ |
|---|---|---|
| รวม/วาดทับ PDF | `pdf-lib` + `@pdf-lib/fontkit` | pure JS รันบน Vercel ได้ |
| หาพิกัดข้อความ (วิธี B) | `pdfjs-dist` | อ่านอย่างเดียว |
| เรนเดอร์หน้ารับรอง (วิธี A) | Puppeteer (มีอยู่แล้ว) | **ต้องรันใน route handler เท่านั้น** ห้ามใน Server Component |
| ฟอนต์ไทย | Sarabun TTF | embed เข้าไฟล์ |

## 5. ความถูกต้องของไฟล์ (ข้อที่จะทำให้ผ่าน audit สบาย)

- เก็บ **SHA-256** ของไฟล์ที่ประกาศใช้ → พิสูจน์ได้ว่าไฟล์ไม่ถูกแก้หลังอนุมัติ
- หน้ารับรองมี **QR code** ชี้ไปหน้าสาธารณะ `/qms/verify/<id>`
  แสดง: รหัส, ชื่อ, ครั้งที่แก้ไข, สถานะ (ใช้งาน/ยกเลิก), ใครอนุมัติเมื่อไร
  → ใครถือกระดาษอยู่ สแกนแล้วรู้ทันทีว่าเป็นฉบับปัจจุบันไหม
  → ตอบโจทย์ข้อ 3.3) "สำเนาไม่ควบคุม ใช้ได้เฉพาะวันที่พิมพ์" ได้ตรงมาก
- ไฟล์ที่ประกาศแล้วบน Drive → สิทธิ์ **อ่านอย่างเดียว** ทุกคน ยกเว้น DCC

## 6. การยกเลิก / เอกสารล้าสมัย (ข้อ 3.4)

พอประกาศฉบับใหม่ ระบบทำอัตโนมัติ:
1. ฉบับเดิม → `status = obsolete`, บันทึกวันที่ + ชี้ไปฉบับใหม่
2. ย้ายไฟล์ไปโฟลเดอร์ "เอกสารยกเลิก" บน Drive + จำกัดสิทธิ์เฉพาะ DCC/QMR
3. ประทับลายน้ำ **OBSOLETE** ทับทุกหน้า (`pdf-lib` ทำได้)
4. เก็บไว้ 3 ปีแล้วค่อยเตือนให้ทำลาย

## 7. แผนการทำ

### Phase 1 — ใช้งานได้จริง (ขั้นต่ำที่ครบวงจร)
- ตาราง `qms_documents`, `qms_approvals`, `qms_events`
- หน้า DCC: อัปโหลด PDF + กรอกข้อมูล + เลือก 3 คน + ส่งอนุมัติ
- หน้าพนักงาน: รายการรออนุมัติ → เปิดดู PDF → อนุมัติ/ตีกลับ
- แจ้งเตือน LINE + ในระบบ ตามลำดับขั้น
- **วิธี A**: สร้างหน้ารับรอง + รวมไฟล์ + ขึ้น Drive
- หน้าทะเบียนเอกสาร (= FM-DCC-01-04) ค้นหา/กรองได้

### Phase 2 — ลดงานมือ
- ตารางสิทธิ์ `qms_authority_matrix` + เติมชื่อผู้อนุมัติอัตโนมัติจากรหัสเอกสาร
- **วิธี B**: เซ็นลงหน้าปกจริงด้วย marker
- QR + หน้า verify สาธารณะ + SHA-256
- ยกเลิกเอกสาร + ลายน้ำ OBSOLETE อัตโนมัติ

### Phase 3 — ครบตาม PM-DCC-01
- ใบ DAR (FM-DCC-01-02) + ทะเบียน DAR (FM-DCC-01-03)
- ทะเบียนเอกสารภายนอก (FM-DCC-01-06)
- เตือนทบทวนประจำปี (กิจกรรมที่ 11)
- รายงานสรุปการเปลี่ยนแปลงประจำปี (กิจกรรมที่ 10)

## 8. เรื่องที่ต้องตัดสินใจก่อนเริ่ม

1. **ลำดับที่ใช้** — ยืนยันว่าใช้ ผู้จัดทำ → ผู้ทบทวน → ผู้อนุมัติ (ตามเอกสาร ISO) ใช่ไหม
2. **ตีกลับแล้วไปไหน** — ที่ออกแบบไว้คือกลับมาที่ DCC ทั้งหมด (เพราะ DCC คือคนถือไฟล์)
   หรืออยากให้ย้อนทีละขั้น?
3. **ลายเซ็น** — ใช้ลายเซ็นจากโปรไฟล์ที่ทำไว้แล้ว ถ้าใครยังไม่ได้ตั้ง
   ระบบควรบังคับให้ตั้งก่อนกดอนุมัติครั้งแรก
4. **ใบ DAR** — ทำใน Phase 3 หรือจำเป็นต้องมีตั้งแต่ Phase 1?
   (PM-DCC-01 บังคับให้มี DAR ก่อนดำเนินการ ยกเว้น QMR อนุมัติยกเว้น)
